# 业务模式的受控源码修复候选

本能力默认关闭，只修改本地业务 SQLite 账本中的隔离源码副本。管理员为员工明确选择一个已审核的修复类型后，该员工可独立提出、验证、应用和回退；无需每一步重新找管理员。暂停接入、身份、时效、项目范围和操作记录继续由同一业务权限系统管理。此候选尚未发布，真人飞书与实际 Codex 仍需验收。

## 管理员开启范围

在新的隔离实例的私有 employee.json 中增加：

```json
"repair": {"profile": "single-select-decoder-v1", "allow_apply": true}
```

这是一项独立授权，与 allow_plans 和付费任务执行开关分开。省略 repair 则完全不开放；allow_apply=false 只允许查看。修改修复范围须重新 inspect/start 核对启动摘要。已绑定员工策略的旧实例不会悄悄接受权限扩大，应保留旧目录，另建隔离实例。不要开启 execute-approved 来进行本修复试验。

当前类型只支持已打包的单选状态解析器：把“一项字符串数组”识别为状态，同时继续拒绝空数组、多值、嵌套数组和其他类型。这是从历史问题提炼的产品源码样例，并非完整的客户生产模块或整个 n8n 图。管理员不能通过配置文件、模型参数或任意路径注入其他源码。

## 员工修复流程

1. 调用 repair/inspect，查看当前源码、摘要、版本和允许范围。
2. repair/propose 只接收 request_id 与 source_fingerprint，由服务器生成固定修复及源码 diff。不能传入代码、Shell、路径、凭据、目标项目或生产工作流 ID。
3. repair/validate 需要 candidate_id、expected_version 和新的 request_id。在独立 Python 进程中执行候选实际源码和固定合成用例；旧源码应失败，修复后应通过。检查十条记录、分页、重复记录及原审核/任务引用保留，禁止外部 I/O。
4. repair/apply 使用返回的新候选版本。仅最近十分钟、当前会话授权和当前源码匹配的通过证明有效；应用只更新隔离账本，业务任务、模型队列、生产源码和调度不改。
5. repair/rollback 同样需要精确候选版本。只有当前副本仍等于该候选应用结果才能回退；不会覆盖之后的修改。源版本递增，旧候选不会因此重新有效。

每步的请求标识只能对应一个请求。请求结果未知时先查 inspect 和既有回执；同请求重放只返回历史回执及当前副本，不能当作再次执行。候选和请求数量有上限，不自动清空账本。所有修复操作同时记入业务审计和带摘要链的修复记录，使用本次员工身份；内部 Agent 与外部 MCP 均应调用相同员工 API，不自行执行补丁。

暂停和恢复作废旧凭据；恢复后重新配对、重新验证。重启也作废此前的验证授权，已应用的隔离副本与历史记录保留。回退只影响源码副本，不撤回脚本审核或已批准任务。验证过程中撤权，会拒绝提交验证结果。

## 安装与验收

仍使用同版本 Python 业务安装包；无 n8n、Docker 或服务器 Node 要求。外部员工 MCP 客户端单独要求 Node.js 22。私有配置由管理员持有，员工无需访问安装目录或管理员密码。

当前只证明特定源码类型在真实业务账本中的隔离修复。它没有生产部署入口，不会把只读工作流快照当作可执行源码，也不支持任意工作流生成的自由补丁。真人独立接手、其他修复类型及生产部署需各自的后续验证。
