# 复用已有 n8n：产品路线与验收边界

开发与逐路线验收跟踪：[Issue #47](https://github.com/ChuluuMGL/video-factory/issues/47)。

Video Factory 的目标是让用户选用已有 n8n（本机 Node.js、本机 Docker、服务器或 n8n Cloud）和飞书 Base，不要求因为安装本产品而重装 n8n 或购买指定操作系统的服务器。首次问答先识别现状；缺少 n8n 时再引导选择安装方式。n8n 的网页编辑器并不代表运行位置，Agent 应确认实例所在位置与 API 能力。

## 当前可做什么

当前固定包能在 Ubuntu 24.04 x86_64 自动部署一套完整栈，包含产品账本、PostgreSQL、自带 n8n 和按需启用的私网 Runner；同一客户可新增项目。`vfctl discover` 已支持对**明确指定**的 n8n API 和飞书 Base 作只读盘点。Skill 中的 `scripts/choose_install_path.py` 能先问选择题并给出当前可完成的路线，不收密钥、不改远端。它们都不是现有 n8n 的完整接入。

现有独立 n8n 目前不能仅凭导入 JSON 就安全跑通本产品的任务。正式调度仍在产品自带 n8n 内安装工作流，并调用私网 Runner；脚本与视频的版本、人工审核、付费授权、失败续接和回执由产品账本维护。旧的导出样板引用尚未交付的执行端点，不能当作可直接导入的客户安装包。

## 分层接入，不让用户重复安装

| 层次 | 用户已经有的 | 还需补齐和验证的 |
|---|---|---|
| 识别 | 任意位置的 n8n、飞书应用/Base | 实例地址、API 权限、版本、网络可达性和表字段；只读，不导入工作流 |
| 工作流 | n8n 本机或 Cloud | 可审阅的版本化 JSON、项目命名空间、禁用状态导入、凭据绑定、激活和回滚；不触碰原工作流 |
| 执行与状态 | 用户自己的计算环境 | 商品与任务账本、幂等回执、脚本/视频执行端点和存储；不能把 n8n 本身误认为这些组件 |
| 审核 | 飞书 Base | 原任务表字段、人员权限、事件订阅、脚本/成片回写与真人验收 |

目标路径：本机 Docker n8n 优先复用本机实例并将产品执行组件部署到同一可信环境；已有服务器 n8n 优先在其可达的私网内放置执行组件；n8n Cloud 需要一个可从 Cloud 安全访问的客户执行端点，且确认套餐开放公共 API。纯 Node.js 本机 n8n 可做单机试用，但常驻执行、备份和 HTTPS 仍需单独规划。当前发行包尚未实现这些部署组合，不得把它们写成“已支持”。

## 开发与验收顺序

1. 对四类已有 n8n 建立只读能力检查，明确 API、网络与飞书状态；没有 API 权限时给出可操作的下一步，不请求完整管理员凭据到 Agent 对话。
2. 将工作流导入与产品栈解耦：新建专用项目空间、默认禁用、记录导入前后差异和回滚标识，绝不覆盖用户原工作流或凭据。
3. 把调度目标从 Docker 私网地址抽象为受认证的产品执行端点。分别实现同机、私网服务器与 Cloud 的安全连接；账本和 Runner 可不与 n8n 同机。
4. 先用合成数据完成安装、中断续接、升级、回滚和重复提交保护，再用授权测试 Base 逐条核对真实脚本、人工审核与视频调用。每种运行方式独立出具验收记录。

只有目标方式通过完整验收，Skill 和官网才把它标为“可安装”；在此之前，Agent 应说明已完成的盘点结果与缺口，不强制用户购买 Ubuntu 主机，也不以单独的 n8n 登录页作为产品成功回执。
