# 复用已有 n8n：产品路线与验收边界

开发与逐路线验收跟踪：[Issue #47](https://github.com/ChuluuMGL/video-factory/issues/47)。

Video Factory 的目标是让用户选用已有 n8n（本机 Node.js、本机 Docker、服务器或 n8n Cloud）和飞书 Base，不要求因为安装本产品而重装 n8n 或购买指定操作系统的服务器。首次问答先识别现状；缺少 n8n 时再引导选择安装方式。n8n 的网页编辑器并不代表运行位置，Agent 应确认实例所在位置与 API 能力。

## 当前可做什么

[a36 便携路线](PORTABLE_N8N.md) 已实现本机 Node.js/Docker 安装、已有 n8n 公共 API 接入和连续问答配置。Windows、Mac、Linux、Linux Docker 均通过真实 n8n 合成流程测试。工作流在 n8n 内直接连接飞书与模型，不要求另装产品服务器、PostgreSQL 或私网 Runner。n8n 自带数据表保存项目执行锁和待写回结果，客户原工作流、数据库与凭据不变。

运行 `scripts/portable_n8n.py welcome`，完成连接、凭据配置、字段补齐和关闭状态的脚本/视频/查询/恢复工作流导入。同一负责人的真实事件、单次费用计划、首次自动脚本生成与写回及本人审核已通过；第二账号权限、非作者安装和桌面实际退出/登录仍待验。Cloud SaaS 本轮跳过，不能声称已实测。

服务器完整栈使用 Ubuntu 完整栈与 `vfctl`，不得将它的安装命令与便携路线混用。下方是后续验收设计，不是要求便携用户先买服务器。

## 分层接入，不让用户重复安装

| 层次 | 用户已经有的 | 还需补齐和验证的 |
|---|---|---|
| 识别 | 任意位置的 n8n、飞书应用/Base | 实例地址、API 权限、版本、网络可达性和表字段；只读，不导入工作流 |
| 工作流 | n8n 本机或 Cloud | 可审阅的版本化 JSON、项目命名空间、禁用状态导入、凭据绑定、激活和回滚；不触碰原工作流 |
| 执行与状态 | 用户自己的计算环境 | 轻量路线先用 n8n + 飞书完成最小闭环；可靠路线再补商品与任务账本、幂等回执、脚本/视频执行端点和存储 |
| 审核 | 飞书 Base | 原任务表字段、人员权限、事件订阅、脚本/成片回写与真人验收 |

目标路径：本机 Docker n8n 优先复用本机实例并将产品执行组件部署到同一可信环境；已有服务器 n8n 优先在其可达的私网内放置执行组件；n8n Cloud 需要一个可从 Cloud 安全访问的客户执行端点，且确认套餐开放公共 API。纯 Node.js 本机 n8n 可做单机试用，但常驻执行、备份和 HTTPS 仍需单独规划。这些是完整栈的后续组合设计；当前便携路线直接在 n8n 内执行工作流，不要求额外产品执行端点。

## 开发与验收顺序

1. 对四类已有 n8n 建立只读能力检查，明确 API、网络与飞书状态；没有 API 权限时给出可操作的下一步，不请求完整管理员凭据到 Agent 对话。
2. 先交付轻量路线所需的可审阅工作流 JSON、飞书字段映射及凭据向导，逐节点核对写回、人工审核与失败状态；不要求先装产品账本。
3. 将工作流导入与产品栈解耦：新建专用项目空间、默认禁用、记录导入前后差异和回滚标识，绝不覆盖用户原工作流或凭据。
4. 可靠路线把调度目标从 Docker 私网地址抽象为受认证的产品执行端点。分别实现同机、私网服务器与 Cloud 的安全连接；账本和 Runner 可不与 n8n 同机。
5. 先用合成数据完成安装、中断续接、升级、回滚和重复提交保护，再用授权测试 Base 逐条核对真实脚本、人工审核与视频调用。轻量与可靠路线、每种运行方式分别出具验收记录。

只有目标方式通过完整验收，Skill 和官网才把它标为“可安装”；在此之前，Agent 应说明已完成的盘点结果与缺口，不强制用户购买 Ubuntu 主机，也不以单独的 n8n 登录页作为产品成功回执。
